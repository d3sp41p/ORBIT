# ORBIT — ТЗ и план разработки

> Копия документа, вставленная владельцем в чат 2026-10-08. Главный документ — оригинал; при изменениях обновлять эту копию.

## Цель и критерий готовности

Нужно превратить прототип ORBIT в рабочий сайт, подключённый к реальной монете на Solana: каждый холдер — планета, данные берутся из блокчейна, планеты живут симуляцией на сервере, новости пишет ИИ, владелец может настроить свою планету через кошелёк. Финальная версия сайта — только на английском.

Работа считается законченной, когда:

- Сайт открыт на своём домене и показывает реальных холдеров монеты; новый покупатель появляется в системе не позже чем через 2 минуты после покупки.
- Размер планеты, орбита, продажи и катастрофы считаются по реальным транзакциям, по правилам из раздела «Данные с блокчейна».
- Симуляция работает на сервере 24/7, одинаково для всех посетителей; новости появляются в ленте без перезагрузки страницы.
- Новости и летопись пишет Claude по фактам симуляции; при сбое ИИ показывается шаблонный текст, сайт не ломается.
- Подключение Phantom и Solflare, подпись сообщения и настройка имени, вида, столицы и девиза работают только для своей планеты.
- В интерфейсе, коде и метаданных нет русского текста; переключателя языка нет.
- Сайт держит 60 fps на среднем ноутбуке и не ниже 30 fps на телефоне среднего уровня.
- Пройден чеклист приёмки из раздела «Тестирование».

Концептуальное ТЗ с идеями и обоснованиями — в документе «ORBIT — ТЗ». При расхождении главный этот документ.

## Что передаётся и как работать с Claude Code

Прототип — рабочий эталон поведения и вида. Его логику не придумывают заново, а переносят в нормальный проект и подключают к реальным данным.

| Файл | Что это | Как использовать |
| --- | --- | --- |
| ORBIT_prototype.html | Весь прототип одним файлом: 3D-сцена, шейдеры, симуляция, тексты событий, карточка, поиск, настройка планеты | Положить в репозиторий в reference/. Источник шейдеров, формул и текстов. Русский словарь и переключатель языка при переносе удалить |
| CLAUDE.md | Инструкция для Claude Code: что за проект, правила, порядок работы | Положить в корень репозитория. Claude Code читает её автоматически в каждой сессии |
| Этот документ | ТЗ и план | Отдавать Claude Code по одному этапу из раздела «План работ» |

Как вести работу:

1. Создать репозиторий на GitHub, положить туда CLAUDE.md и прототип, открыть проект в Claude Code.
2. Давать задачи по одному этапу: скопировать текст этапа из раздела «План работ» и попросить сначала план, потом реализацию.
3. После каждого этапа проверить критерии приёмки руками, сделать коммит и только потом переходить дальше.
4. Любое решение, которое меняет правила игры (формулы, пороги, тексты), сначала согласовать с владельцем, потом записать в этот документ.
5. Ключи и секреты никогда не вставлять в чат и в код: только в .env.local и в настройки хостинга.

## Архитектура

Воркер — единственное место, где считаются правила игры: он забирает события сети от Helius, ведёт симуляцию, заказывает тексты у Claude и пишет всё в Supabase. Сайт читает данные через API и получает новые события через Realtime; запись с сайта — только настройки своей планеты после подписи кошельком.

## Стек, сервисы и переменные окружения

Один репозиторий (монорепо): сайт на Next.js и отдельный фоновый воркер. Общий код (симуляция, тексты событий, типы) лежит в общем пакете и используется и сервером, и сайтом.

| Часть | Технология | Где работает |
| --- | --- | --- |
| Сайт и API | Next.js (App Router), TypeScript, three.js (перенос кода прототипа) | Vercel |
| Воркер | Node.js + TypeScript: индексер, тики симуляции, очередь ИИ | Railway или Fly.io, всегда включён |
| База и живые обновления | Supabase: Postgres + Realtime | Supabase |
| Данные Solana | Helius: RPC, DAS API, вебхуки | Helius |
| ИИ-тексты | Claude API, модель Claude Haiku 5.5 (claude-haiku-5-5) | Anthropic |
| Кошелёк | Solana Wallet Adapter (Phantom, Solflare), подпись сообщения | Браузер |
| Ошибки и аналитика | Sentry, Vercel Analytics или Plausible | — |

Структура репозитория:

## Данные с блокчейна

Все правила игры опираются на эти определения. Их надо реализовать точно и покрыть тестами на записанных реальных транзакциях.

### Холдер

- Холдер — это кошелёк-владелец (owner), а не токен-аккаунт. Балансы всех токен-аккаунтов одного владельца по TOKEN_MINT суммируются.
- Планетой становится холдер с балансом не меньше MIN_HOLDING_TOKENS. Ниже порога планета не создаётся или исчезает так же, как при полной продаже.
- Кошельки из EXCLUDED_WALLETS в систему не попадают: пул ликвидности, bonding curve, адрес сжигания, кошельки команды и известных бирж, если владелец так решит.

### Время холда и орбита

- Начало холда — момент, когда баланс перешёл через порог снизу вверх. Докупки начало не меняют.
- Если баланс упал до нуля (или ниже порога), планета погибает. Повторная покупка создаёт новую планету: внешний вид тот же (он из адреса), но прогресс и время холда с нуля. История прошлой жизни сохраняется в архиве.
- Номер орбиты — место холдера в списке по времени холда: самый давний ближе всего к звезде. Радиус считается по формуле прототипа (34 + f^0.82 × 520, где f — доля от числа холдеров).

### Ранг и размер

- Ранг — место по балансу среди всех холдеров. Пересчитывается при каждом снапшоте.
- Класс и размер по рангу берутся из прототипа (classOf, sizeOf): 1 — сверхгигант, 2–10 — газовые гиганты, 11–50 — ледяные гиганты, 51–200 — каменные, остальные — астероиды. Смена ранга меняет размер плавно (анимация на фронте).

### Покупки, продажи и переводы

- Источник событий — вебхуки Helius по TOKEN_MINT (свопы и переводы) плюс сверочный снапшот раз в минуту, чтобы ничего не потерялось.
- Покупка: баланс вырос. Счётчик покупок +1, в ленте — комета к планете.
- Продажа: баланс уменьшился. Доля продажи = проданное / баланс до продажи. Меньше sellIgnoreBelow (2%) — без последствий; иначе — катастрофа по правилам симуляции.
- Перевод на другой кошелёк считается продажей у отправителя и покупкой у получателя. Это прямо написано в FAQ.
- Обработка идемпотентна: ключ — подпись транзакции + индекс инструкции. Повторный вебхук не должен создавать второе событие.

### Монета

- Капитализация = цена × обращающийся запас. Источник цены — DAS/цена Helius или DEX-агрегатор; обновлять раз в минуту. Класс звезды считается по порогам из прототипа (STAR_TIERS).
- Если монета ещё на bonding curve pump.fun, адрес кривой добавить в исключения; после миграции в пул — добавить адрес пула. Уточнить у владельца, где сейчас монета.

**Первая загрузка.** При старте воркер берёт полный список токен-аккаунтов через DAS, восстанавливает историю покупок и продаж по каждому холдеру (история подписей и разбор транзакций) и прогоняет симуляцию от начала холда до текущего момента. Это разовая тяжёлая операция; делать батчами с паузами, чтобы не упереться в лимиты Helius.

## Симуляция планет

Эталон — функции initSim, step, chooseEvent, applyEvent, applySell, eraOf, hab, lifeChanceDay из прототипа. Их переносят в /packages/core на TypeScript без изменения формул, а затем убирают всё, что зависит от браузера.

### Главные правила

- Симуляция идёт только на сервере. Сайт получает готовое состояние и события; сам ничего не считает.
- Детерминизм: генератор случайных чисел инициализируется из wallet + life_no (как rngFor(addr+"sim")), его состояние хранится в planet_state.rng_state. Одинаковые входные данные дают одинаковую историю. Это нужно для тестов и пересчётов.
- Тик — каждые 4 часа от начала холда каждой планеты (tickHours: 4). У разных планет тики сдвинуты, поэтому новости в системе идут равномерно.
- Воркер раз в минуту берёт планеты с next_tick_at <= now(), прогоняет нужное число тиков, сохраняет состояние и события одной транзакцией.
- Продажа применяется в ближайший тик после неё (как applySell в начале step).

Параметры баланса (вынести в /packages/core/config.ts, менять только там):

| Параметр | Значение | Смысл |
| --- | --- | --- |
| tickHours | 4 | шаг симуляции |
| eventChance | 0.33 | шанс события за тик (у астероидов ×0.35) |
| rareChance | 1/6000 | шанс редкой находки за тик |
| speed | 1.0 | общий множитель роста технологий |
| sizeBonusMax | 2.0 | бонус топ-1 к стабильности и технологиям |
| sellPenalty | 1.0 | откат прогресса при продаже |
| sellIgnoreBelow | 0.02 | продажи меньше 2% без последствий |
| ringsAfterDays | 30 | кольца за 30 дней без продаж |

Состояние планеты: температура, вода, атмосфера, жизнь (есть / нет, день появления), биосфера, цивилизация (есть / нет, тип, библия), население, технологии, стабильность, пепел, затемнение огней, луны, колонии, находки. Эпоха вычисляется из состояния (eraOf) и может откатываться.

Что проверить отдельно:

- Распределение на 650 тестовых холдерах как в прототипе: примерно треть каменных планет без жизни, единицы в эпохе «Megastructure», находки примерно у 7%.
- Технологии и население не уходят в бесконечность (в прототипе это было исправлено затуханием 1/(1+tech×0.35)).
- Полная продажа: событие гибели, планета уходит в архив, на её месте на фронте остаётся облако обломков на 24 часа.
- Визуальные параметры для шейдера (syncVisual: lava, water, bio, city, ice, ash, dim) вычисляются из состояния одной функцией в /packages/core.

## Новости, лор и ИИ

Симуляция решает, что произошло; ИИ только пишет текст по фактам. Цифры в тексте всегда из params события.

### Конвейер

1. Тик создаёт событие в planet_events со шаблонным английским текстом (шаблоны EV.en из прототипа). Новость видна сразу.
2. Если событие подходит под правило «писать ИИ», оно попадает в очередь. Воркер берёт очередь пачками и вызывает Claude Haiku 5.5.
3. Ответ проверяется: длина до 280 символов, все числа из params присутствуют, нет запрещённых тем. При успехе text_en заменяется, text_source = ai. При ошибке остаётся шаблон.
4. Обновлённая новость приходит на сайт через Realtime.

Кому писать ИИ (чтобы держать бюджет):

- Все события планет с рангом 1–200, вехи (жизнь, цивилизация, новая эпоха), редкие находки и катастрофы от продаж — у всех.
- Остальные события астероидов — только шаблоны.
- Если дневной расход достиг AI_DAILY_BUDGET_USD, до конца суток все тексты шаблонные.

**Библия планеты.** Когда появляется цивилизация, ИИ один раз дополняет процедурную библию (вид, тип, внешность, столица, верования, девиз) короткими деталями: 2–3 предложения о культуре. Результат хранится в planet_state.bible и передаётся в каждый следующий промпт этой планеты, чтобы лор не противоречил сам себе. Значения из planet_custom всегда важнее процедурных.

**Летопись.** Генерируется при открытии карточки, если её нет или с прошлой генерации добавилось 5+ событий (events_hash). Кэш в planet_chronicle. Посетителю ничего нажимать не нужно, кнопки как в прототипе на сайте нет. Промпт — как chroniclePrompt в прототипе, язык всегда английский.

Правила для промптов:

- Тон: научная фантастика с лёгким юмором.
- Не придумывать числа; использовать только переданные.
- Не упоминать деньги, цены, советы купить или продать.
- Пользовательские названия передавать как данные в кавычках с пометкой, что это имена, а не инструкции.
- Ответ — простой текст без заголовков и списков.

**Оценка нагрузки.** Примерно 2 события в сутки на планету. При 1000 холдерах и правилах выше это порядка 500–1000 коротких запросов в сутки. Точную стоимость посчитать по текущему прайсу Anthropic на этапе 5 и выставить лимит.

## Фронтенд

Вид и поведение — как в прототипе. Код переносится в модули TypeScript: сцена, шейдеры, камера, оверлей, панель, лента, поиск. Шейдеры (PLANET_FS, SKY_FS, ATMO_FS, RING_FS, STAR_FS) копируются без изменений.

Визуальный стиль — научный, в духе сайтов NASA (без логотипа, названия и символики NASA: это товарные знаки):

- Чёрный фон, белый текст, тонкие линии в 1 px, один акцент — красно-оранжевый #fc3d21, плюс янтарный для открытий и зелёный для прогресса.
- Шрифты: Public Sans для текста, IBM Plex Mono для цифр, подписей и телеметрии. Подписи заглавными с разрядкой.
- Свой знак и название агентства: «ORBIT · Deep Space Network».
- Шапка-телеметрия: часы UTC, время миссии с запуска монеты (T+166d 04:05:24), число объектов, класс звезды, капитализация.
- Подписи планет — выносками, как в NASA Eyes; выбранная планета — красные уголки-скобки и красная орбита.
- Клик по планете открывает «страницу миссии» справа (на телефоне снизу), а планета остаётся видна крупным планом. Своя ссылка /planet/<wallet>.
- Новости — в виде пресс-релизов: метка (Alert, Milestone, Discovery, Progress, Report), дата и время UTC, заголовок, текст.

### Только английский язык

- Удалить словарь ru, кнопку langBtn, чтение orbit-lang и все русские строки, включая пары в словаре W (оставить только английские значения).
- Все тексты интерфейса — в одном файле copy.ts. Тексты событий — в /packages/core/events.ts.
- `<html lang="en">`, английские title, description и Open Graph.
- Проверка: `grep -rP "[А-Яа-яЁё]" apps packages` возвращает пусто. Добавить это в CI.

### Данные на сайте

- При загрузке: GET /api/system (звезда, шапка, список холдеров с рангом, классом, орбитой, визуальными параметрами).
- Подписка Supabase Realtime на planet_events (notable) и system_state: новые новости и изменения капитализации без перезагрузки.
- Карточка планеты: GET /api/planet/:wallet при открытии; события — постранично.
- Орбитальное движение считать на клиенте от общего времени (angle = angle0 + speed × t), чтобы у всех посетителей планеты стояли в одних местах.

Обязательные элементы интерфейса: шапка (капитализация, число миров, класс звезды, Buy, X), поиск по адресу и имени, «Random world», «Visit #1», общая лента, легенда, зум, страница миссии планеты (ключевые данные, графики, новости, отчёт ИИ, хроника, цивилизация, находки, данные холдера, ачивки), страница звезды, подключение кошелька, форма настройки планеты, страница FAQ и дисклеймер.

### Производительность

- Три уровня качества: high / medium / low. Выбор автоматически по устройству и по fps первых секунд; ручной переключатель в настройках.
- Low: небо 512, без bloom, 4000 звёзд, планеты только средней детализации.
- Полные меши — только для топ-200; остальные холдеры — инстансы астероидов. Если холдеров больше 5000, хвост показывать точками.
- Сцену не рендерить, когда вкладка скрыта.

**Шеринг:** у каждой планеты своя ссылка /planet/<wallet>, которая открывает систему и подлетает к планете. Для неё серверная OG-картинка с именем, классом, эпохой и рангом.

**Доступность:** Escape закрывает карточку, видимый фокус у всех кнопок, prefers-reduced-motion замедляет анимации, основные данные карточки доступны без WebGL (текстовая версия при ошибке WebGL).

## Кошелёк и настройка планеты

Смотреть систему можно без кошелька. Кошелёк нужен только для настройки своей планеты. Никаких транзакций и никаких разрешений на токены сайт не запрашивает.

### Поток входа

1. Кнопка «Connect wallet» (Solana Wallet Adapter: Phantom, Solflare).
2. Сайт запрашивает POST /api/auth/nonce и получает одноразовое сообщение: домен, адрес кошелька, nonce, время, срок действия 5 минут.
3. Кошелёк подписывает сообщение (signMessage).
4. POST /api/auth/verify: сервер проверяет подпись ed25519, домен, срок и что nonce не использован. Выдаёт сессию (httpOnly cookie, 7 дней).
5. После входа появляются кнопки «My planet» (перелёт к своей планете) и «Customize planet» в её карточке. У чужих планет кнопки настройки нет.

Что можно менять: имя планеты, название вида, столицу (до 24 символов) и девиз (до 60). Пустое поле — стоковое значение. Кнопка «Restore defaults» сбрасывает всё.

Проверка на сервере (на клиенте только подсказки):

- Сессия принадлежит владельцу этой планеты, и планета жива.
- Длина, разрешённые символы (буквы, цифры, пробел, дефис, апостроф; в девизе ещё знаки препинания), без ссылок и эмодзи.
- Фильтр нецензурной лексики и оскорблений на нескольких языках (готовая библиотека плюс свой список), включая обходы через цифры и пробелы.
- Не чаще одного изменения в сутки.

**Модерация:** у каждой планеты кнопка «Report name». Админ (кошелёк из ADMIN_WALLETS) видит список жалоб и может скрыть пользовательские названия (hidden_by_admin) — тогда показываются стоковые.

**Где применяются названия:** карта, поиск, карточка, все новости (включая старые), летопись и промпты ИИ. При полной продаже настройки уходят в архив вместе с планетой.

## Безопасность и надёжность

### Безопасность

- Секретные ключи (SUPABASE_SERVICE_ROLE_KEY, HELIUS_API_KEY, ANTHROPIC_API_KEY) только на сервере; в браузер попадает только анонимный ключ Supabase. Проверить сборку: в клиентских бандлах нет секретов.
- RLS в Supabase включён на всех таблицах; клиенту разрешено только чтение публичных данных. auth_nonces, ai_usage, жалобы — без доступа с клиента.
- Вебхук Helius принимается только с правильным секретом в заголовке.
- Ограничение частоты запросов: auth — 10 в минуту с IP, report — 5 в час, custom — 1 в сутки на кошелёк.
- Пользовательский текст всегда экранируется при выводе (в прототипе есть esc), никогда не вставляется как HTML.
- Пользовательские названия в промптах ИИ передаются как данные, не как инструкции.
- Сайт никогда не просит подписать транзакцию. На странице FAQ прямо написать: «We will never ask you to sign a transaction».

### Надёжность

- Пропущенные вебхуки: сверочный снапшот раз в минуту сравнивает балансы и досоздаёт недостающие события.
- Воркер упал: после перезапуска догоняет все просроченные тики по next_tick_at; результат тот же, что без падения (детерминизм).
- ИИ недоступен или исчерпан бюджет: шаблонные тексты, очередь копится и разбирается позже.
- Helius недоступен: сайт показывает последнее известное состояние и плашку «Live data delayed».
- Ежедневный бэкап базы (Supabase), мониторинг /api/health (UptimeRobot или аналог) с уведомлением владельцу.

## План работ по этапам

Каждый этап отдаётся Claude Code отдельной задачей. Следующий этап начинается только после того, как приняты критерии предыдущего.

1. **Подготовка.** Монорепо (apps/web, apps/worker, packages/core), TypeScript, ESLint, Prettier, CI на GitHub Actions (сборка, тесты, проверка на кириллицу). Аккаунты Vercel, Supabase, Helius, Anthropic, Railway. .env.example.
    - Приёмка: пустой сайт деплоится на Vercel, воркер запускается на Railway, CI зелёный.
2. **Перенос фронтенда на тестовых данных.** Сцена, шейдеры, небо, карточки, поиск, лента из прототипа — в модули Next.js. Только английский. Данные пока из генератора прототипа.
    - Приёмка: сайт выглядит и ведёт себя как прототип; русского текста нет; 60 fps на ноутбуке; уровни качества работают.
3. **Ядро симуляции.** Перенос симуляции в packages/core, детерминированный RNG с сохраняемым состоянием, юнит-тесты.
    - Приёмка: один и тот же вход даёт одну и ту же историю; распределение эпох на 650 тестовых холдерах как в прототипе; тесты зелёные.
4. **База и индексер.** Миграции, первая загрузка холдеров через DAS, восстановление истории, вебхуки Helius, сверочный снапшот, ранги, время холда, капитализация.

5. **Симуляция на сервере и живой сайт.** Тики в воркере, сохранение состояния и событий, API, Realtime, переключение фронтенда на реальные данные.

6. **ИИ-новости и летопись.** Очередь, Claude Haiku 5.5, проверка ответа, бюджет, библия, летопись при открытии карточки.

7. **Кошелёк и настройка.** Вход подписью, сессии, форма настройки, проверка, жалобы, админка.
    - Приёмка: свою планету можно настроить, чужую нельзя (проверить и через прямой запрос к API); запрещённые слова отклоняются; названия меняются во всех местах.
